# Provider identity reuse: Windows, WSL and parallel worktrees

Read-only investigation, October 11, 2026. This is a recommendation for evaluation, not an implemented adapter or permission to transfer credentials. No authentication contents were read, hashed, copied, linked or published; no login, logout, token generation or credential-access change was performed. The operator is not asked to log in again until a reuse strategy is chosen.

## Observed installations and storage metadata

| Surface | Installed CLI | Observed default credential path |
| --- | --- | --- |
| Windows `admin` | Codex 0.162.1 | `C:\Users\admin\.codex\auth.json` exists |
| Ubuntu `alex` | Codex 0.157.0, Node 24.21.0 | `/home/alex/.codex/auth.json` exists, regular non-symlink, owner UID 1000, mode 0600 |
| Windows `admin` | Claude Code 2.1.296 | `C:\Users\admin\.claude\.credentials.json` exists |
| Ubuntu `alex` | Claude Code 2.1.296 | `/home/alex/.claude/.credentials.json` absent |

No `CODEX_HOME` or `CLAUDE_CONFIG_DIR` override was observed in the inspected processes. Existence does not establish that a particular file is the active backend or that its login is valid. Pinned help confirms Codex `login --device-auth`, `login --with-access-token`, and experimental `app-server`; Claude confirms `auth login` and `setup-token`. These help commands did not initiate authentication.

Different job `cwd` values do not create separate provider identities. A permanent home/profile outside worktrees avoids per-task login. A new Linux UID is a different credential boundary and does not automatically inherit the Windows account's cached login.

## Supported mechanisms and their limits

[Codex authentication documentation](https://learn.chatgpt.com/docs/auth) describes cached file/keyring storage, `CODEX_HOME`, and a one-time auth-cache transfer to a headless host. Windows credential-store entries are not automatically available to Linux. The documented file transfer is possible only with separately approved credential handling; it is not continuous two-way synchronization. For concurrent automation, [the CI/CD guide](https://learn.chatgpt.com/docs/auth/ci-cd-auth) warns against sharing a cache across jobs/machines because refresh rotation can invalidate another copy. Neither fresh per-job copies nor a writable `/mnt/c` symlink resolve this lifecycle problem.

[Claude authentication documentation](https://code.claude.com/docs/en/authentication) identifies `.credentials.json` under the user/config directory and supports a one-year subscription OAuth token generated by `claude setup-token`, supplied through `CLAUDE_CODE_OAUTH_TOKEN`. It works on Windows and WSL; revocation/expiry can still require renewal. Local MCP remains available, but this token cannot establish Remote Control or use claude.ai connectors; bare mode does not consume it. `apiKeyHelper` supplies API credentials and is not a substitute for the requested subscription. The documentation does not establish safe concurrent refresh locking for a Windows/WSL shared `.credentials.json` file.

## Recommended ownership and parallelism

Keep one persistent credential authority per provider and account, outside target repositories, worktrees, API/PostgreSQL, Compose mounts and telemetry. Agent roles share the provider identity, while retaining independent prompts, immutable configuration, worktrees, execution IDs and budgets. Authentication serialization must not serialize agent execution.

For Codex, evaluate **one persistent WSL app-server under `adf-worker`**, with separate `thread/start` sessions and canonical ext4 `cwd` values. The pinned [0.157.0 message processor](https://github.com/openai/codex/blob/rust-v0.157.0/codex-rs/app-server/src/message_processor.rs) shares an `Arc<AuthManager>` with ThreadManager and request handlers. Its [auth manager](https://github.com/openai/codex/blob/rust-v0.157.0/codex-rs/login/src/auth/manager.rs) has a one-permit refresh semaphore and guarded reload before refreshing. This supports the ownership design by source inspection; it does **not** prove ADF compatibility or a cross-process file lock. Three parallel sessions still need a contract test with the pinned binary. No server was started during this investigation.

If preserving the Windows login as the sole authority is essential, evaluate an authenticated local broker rather than sharing its refresh cache. [App-server external ChatGPT tokens](https://learn.chatgpt.com/docs/app-server) are an experimental integration: a host that already owns the auth lifecycle supplies access tokens and handles refresh requests. This is not an endpoint for extracting the desktop app's credentials. A Windows-to-WSL bridge therefore needs an explicit supported token source, a sole refresh owner, protected IPC and new adapter tests. Existing Windows desktop/CLI clients must not independently rotate a duplicated refresh token. Do not assume Windows 0.162.1 and WSL 0.157.0 protocol compatibility.

For Claude, the practical broker candidate is one separately approved `setup-token` provision, kept in protected operator storage and supplied only to trusted CLI launches. It permits parallel jobs without distributing a rotating login file. It is not implemented: ADF's `restricted_env` currently strips secret variables and rejects `CLAUDE_CODE_OAUTH_TOKEN` in ordinary `env_allowlist`. A trusted launcher channel, explicit redaction registration, expiry handling and child-environment tests would be required. Credentials must never become agent configuration, command arguments, API payloads or trace attributes. Same-UID shell execution is not a strong secret-isolation boundary.

## Adapter gates before adoption

1. Prove three simultaneous native sessions use distinct ext4 worktrees, policy/MCP/skill scopes and event routes while one authority owns authentication. Use controlled fake refresh tests; do not force real credential rotation for diagnostics.
2. Preserve per-execution cancel/timeout. A shared app-server cannot use the current subprocess adapter's whole-session kill as routine cancellation: it would affect sibling jobs. Verify per-thread interrupt, independent child cleanup, ownership proof and reconciliation after broker loss.
3. Prevent cross-thread configuration/skill/MCP/session leakage; preserve exact-tree checks, independent review and commit fencing. Treat protocol upgrades as adapter changes requiring contract tests.
4. Test expired/revoked/unknown auth, concurrent unauthorized responses and broker restart. Stop dispatch for that provider and retain uncertain effects; never silently change provider, model or billing method.
5. Keep Windows/foreign credential permissions unchanged until the exact migration/broker mechanism is approved. No repeated-login requirement is inferred from worktree creation. A one-time dedicated WSL login remains the simplest fallback if authorized reuse cannot be made safe.

This design remains inside the existing runtime-worker responsibility; it does not justify a fifth application repository. See [security](security.md), [operator actions](operator-acceptance.md) and [acceptance status](acceptance-status.md). MVP readiness remains false.
