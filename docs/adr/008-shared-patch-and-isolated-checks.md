# ADR 008: Worker-applied patches and a closed Python checker

Status: Accepted for source-only opt-in implementation, October 11, 2026. Installation and native acceptance are pending separate approval. This does not certify MVP completion or broaden ADR 007's sealed policy.

## Context

SPEC requires parallel developers, checks, bounded repairs, independent review and sequential integration. The existing orchestrator already owns that loop. Pinned Codex workspace-write conflicts with the strict absence guard; the [investigation](../shared-write-path.md) proposed read-only generation plus an authoritative host writer. Independent review also found that registered Python/Node checks on the host can execute patch-controlled code, and an inherited allocation lock descriptor can unlock the supervisor's flock. An argv blacklist cannot enforce filesystem isolation.

## Decision

Implement opt-in `shared-patch` in the worker. Keep original approved `trusted-development` authorization; use `observe` only for native generation. A closed `adf.text-patch.v1` result has at most 16 ordered create/replace/delete edits, exact relative paths, supplied preimage hashes and UTF-8 content. The worker owns application, not the model. Existing planner/reviewer roles cannot call the writer. `shared` retains its sealed native-write refusal.

Use existing Linux `renameat2` no-replace/exchange operations, held no-follow directory FDs, regular single-link files, fsync and durable per-file intents. Preserve raced preimages and unresolved auxiliaries. Death of a supervisor is insufficient for ACK: both terminal delivery and stopped/reconciliation proof must classify every latest intent. Recovery never regenerates or blindly applies remaining edits. A fully known partial cancellation can retain already applied files; an auxiliary/unknown state remains uncertain for manual resolution. Repair transfer goes through the same writer in a fresh allocation.

For checks, construct an empty bubblewrap namespace with a verified staged-file snapshot mounted read-only, only selected Python/toolchain roots, private PID/proc/IPC/network, a cleared environment, no allocation/profile FDs and no host fallback. Run a trusted resource bootstrap before exec. Bound private HOME/scratch tmpfs, file sizes, CPU, descriptor count, locked memory and address space. A trusted read-only namespace entry closes helper descriptors and installs Linux x86-64 seccomp before project code: no fork/clone/threads, io_uring/AIO workers, kernel keyrings, anonymous shmem/SysV IPC/MQ, sockets or selected cross-process/kernel/namespace interfaces. Read-only remounts protect the namespace root and `/dev`; nested user namespaces are disabled. A trusted no-project-code preflight must pass before model generation.

The existing official Codex 0.157.0 package contains the standalone launcher; no new host package, group, sudo/Docker access, listener, firewall or global security change is installed here. Activation requires a **separate operator-owned checker manifest**, not an extension of the existing provider policy. Its launcher hash is `77360cb751ccedc5971391444ac86a8a33c15b04d6b4a6fe45f5d25496e62c4c` (529,776 bytes); CI checks that exact binary from the pinned package. CI uses Ubuntu 22.04 to test ordinary unprivileged namespaces without changing an AppArmor/sysctl policy.

## Explicit limitations

- Writer v1 supports text in existing parent directories only, preserves supported existing modes and creates 0644 files. Binary, rename, symlink/hardlink, mode, new directory, metadata/config/credential edits are refused. Temporary sibling files belong only to the exact authorized file operation; they cannot become model-selected targets or staged artifacts.
- Checker v1 supports the worker's pinned Python only. Its snapshot excludes `.git`, `.agents`, `.codex`, `.claude`, `.github`, credentials, ignored files, project `.venv` and `node_modules`. Bounds are 4,096 files, 2 MiB per file and at most 64 MiB aggregate, further restricted by the original job disk limit. Checks must write temporary outputs through private `HOME`/`TMPDIR`; writing build outputs into the source tree fails.
- `RLIMIT_AS=128 MiB`, `RLIMIT_NOFILE=64`, zero core dumps/locked memory, bounded file size/CPU and bounded tmpfs are conservative limits. Seccomp constrains project code to one process with no threads or subprocess checks. A trial `RLIMIT_NPROC=32` made WSL namespace setup return `EAGAIN` despite five visible UID tasks; it was replaced rather than changing host/global limits. These are not cgroup aggregate CPU/RSS accounting or a general hostile-code sandbox. Node/V8, Docker, networked checks, interactive and generic build runners remain unsupported; they require a separate reviewed resource/isolation design, not silently increased limits.
- Held descriptors and preserved preimages detect accidental concurrent changes but do not sandbox a hostile same-UID host editor/admin. Such trusted processes must honor the allocation lock. Recovery preserves ambiguous files instead of deleting them.
- Native Codex `read-only` prevents writes but **does not prove restricted host reads**. The pin can bind `/` read-only for full-disk read access. Existing scoped MCP v1 is unchanged and cannot disable native shell reads by itself. No secret-read isolation claim is made for model generation. A verified restricted native permission profile or an explicit bounded synthetic acceptance decision is still required before broader deployment; no such permission/profile activation happened in this source work.

## Alternatives and sources

Landlock alone would still require process/network/IPC controls and toolchain visibility. We chose the already pinned namespace launcher for filesystem/network isolation plus an architecture-specific seccomp guard for the closed single-process checker; no kernel configuration was changed. The [Linux Landlock documentation](https://docs.kernel.org/userspace-api/landlock.html) and [seccomp interface](https://docs.kernel.org/userspace-api/seccomp_filter.html) were inspected. Syscall numbers and ABI/filter constants were checked against official [x86-64 syscall definitions](https://github.com/torvalds/linux/blob/v6.18/arch/x86/entry/syscalls/syscall_64.tbl), [seccomp UAPI](https://github.com/torvalds/linux/blob/v6.18/include/uapi/linux/seccomp.h) and [audit UAPI](https://github.com/torvalds/linux/blob/v6.18/include/uapi/linux/audit.h). The [key request service](https://docs.kernel.org/security/keys/request-key.html) explains the kernel helper bypass prevented by denying keyring calls. Seccomp supplements the namespace; it does not establish information-flow isolation by itself.

[Bubblewrap's own security documentation](https://github.com/containers/bubblewrap/blob/main/README.md) makes the constructed mounts/arguments authoritative for protection. The exact installed standalone `--help` confirmed `--size`, `--disable-userns`, `--unshare-user`, `--remount-ro` and namespace options. [Pinned Codex bubblewrap construction](https://github.com/openai/codex/blob/rust-v0.157.0/codex-rs/linux-sandbox/src/bwrap.rs) supports the generation read-scope limitation above. [GitHub's runner reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners) lists Ubuntu 22.04. Sources were checked October 11, 2026; only standalone synthetic checker processes were run, with no Codex/Claude CLI, native thread/turn or model call.
